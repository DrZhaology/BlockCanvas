# 待实施设计：多页工程 + 深色模式插件化

> 这两项都**改架构**，不适合在"顺手改一下"的节奏里做。
> 本文把它们拆到可执行的粒度，下一轮照着做即可，不需要重新调研。
> 顺序建议：**先深色插件化（风险低、纯前端），再多页（动工程格式、要迁移）**。

---

## 一、深色模式插件化

### 现状（已实测）

- 主题开关最终落到 `html[data-bc-dark]` 属性
- 深色覆盖规则**散落在 10 个 CSS 文件、共 31 处**：

  | 文件 | 处数 |
  | --- | --- |
  | `26-empty-home.css` | 7 |
  | `10-settings-projects.css` | 5 |
  | `13-polish-v040.css` | 5 |
  | `14-v04x-append.css` | 5 |
  | `04-workspace-canvas.css` | 2 |
  | `11-editors.css` | 2 |
  | `23-v044d-ui.css` | 2 |
  | `02-tabbar.css` | 1 |
  | `09-class-template-ext.css` | 1 |
  | `25-v044-storage-ui.css` | 1 |

- 问题不在"能不能深色"，而在**加新组件时很容易漏掉深色规则**（新写的卡片在深色下白得刺眼），
  而且同一类颜色（面板底、边框、次级文字）在 31 处里各写各的，值已经开始漂移。

### 目标

把"深色"从"一堆覆盖规则"变成"**一份调色板 + 一套语义变量**"，
新组件只要用语义变量就自动适配，不需要再写 `html[data-bc-dark]` 分支。

### 步骤（每步都可独立提交、可回滚）

**第 1 步：建立语义变量层（不改任何视觉）**

新建 `src/renderer/styles/00-theme-tokens.css`，**第一个**被 import（在 `main.tsx` 里排最前），定义：

```css
:root {
  /* 语义色：所有组件只准用这些，不再直接写 #fff / #e5e7eb */
  --surface-0: #ffffff;   /* 最底层页面 */
  --surface-1: #f8fafc;   /* 面板 */
  --surface-2: #ffffff;   /* 卡片 */
  --surface-sunken: #f1f5f9;
  --line: #e5e7eb;
  --line-strong: #cbd5e1;
  --text-1: #0f172a;
  --text-2: #475569;
  --text-3: #94a3b8;
  --accent: #1e88e5;
  --danger: #dc2626;
  --shadow-1: 0 1px 3px rgba(15, 23, 42, .06);
}
html[data-bc-dark] {
  --surface-0: #0f1420;
  --surface-1: #151b28;
  --surface-2: #1b2231;
  --surface-sunken: #101725;
  --line: #2a3444;
  --line-strong: #3b4759;
  --text-1: #e8edf6;
  --text-2: #a8b4c6;
  --text-3: #6f7d92;
  --accent: #4c9ff0;
  --danger: #f07171;
  --shadow-1: 0 1px 3px rgba(0, 0, 0, .4);
}
```

> 关键：这一步**只新增文件、不改任何现有规则**，所以视觉零变化，风险为 0。
> 提交后可以立刻截图对比确认"看起来一模一样"。

**第 2 步：把 31 处覆盖逐文件"翻译"成语义变量**

按文件逐个改，每改一个文件提交一次（方便单独回滚）：

1. 打开该文件，搜 `data-bc-dark`
2. 每条规则里的颜色值 → 换成对应的语义变量
3. 换完后，**如果这条 `html[data-bc-dark]` 规则变成空的了，就删掉它**
4. 跑 `node tests/e2e/probe-uiaudit.mjs` + 手工切一次深色看一遍

目标：31 处 → 0 处（或只剩极少数确实需要"仅深色"的特殊规则，比如发光效果）。

**第 3 步：做成真正的插件**

- `extensions/theme-dark/manifest.json`：声明 `type: 'theme'`，提供 `tokens` 段
- 主进程在加载扩展时，把 theme 类型的 `tokens` 合并进 `:root` / `html[data-bc-dark]`
- 内置主题仍然走同一套机制（`extensions/theme-dark` 作为内置插件随包分发）
- 插件可覆盖任意语义变量 → 用户能自己写一个"暗紫主题"

**第 4 步：加一条防回归探针**

在 `probe-uiaudit.mjs` 里加：

- 切到深色后，`--surface-1` 与 `--text-1` 必须真的变化
- 抽查 3 个关键容器（`.panel`、`.pc-card`、`.toolbar`）的 `background-color`
  必须来自语义变量（即与 `--surface-*` 的 computed 值一致）
- 新增组件若写了裸色值，这条探针抓不到——所以配一条 **lint 约定**：
  CSS 里禁止新增 `#fff` / `#ffffff` / `#000` 这类裸值（用 `rg` 做检查脚本）

### 风险与回滚

- 第 1 步零风险（纯新增）
- 第 2 步逐文件提交，任何一步视觉不对就回滚那一个文件
- 第 3 步如果卡住，前两步的成果仍然有效（语义变量本身就有价值）

## 二、多页工程

### 现状（已实测）

- `SCHEMA_VERSION = 2`，容器结构：`manifest.json` + `scene.json` + `assets/` + 任意 section
- `scene.json` 里只有**一棵** `root` 树
- 导出：一个 HTML 文件
- 快照/历史都是整包 `.bcproj`

### 目标

一个工程里有多页，可切换、可增删、可分别导出，**老工程打开照旧**。

### 数据结构（关键决策）

**不新建一套并行结构**，而是把 `scene.json` 从"一棵树"升级成"一页 + 页表"：

```jsonc
// scene.json（v3）
{
  "pages": [
    { "id": "p_home", "name": "首页", "path": "index.html", "root": { ...树... } },
    { "id": "p_about", "name": "关于", "path": "about.html", "root": { ...树... } }
  ],
  "activePageId": "p_home",
  "tokens": [...],          // 全站共享（变量本来就该跨页）
  "quickCss": "...",        // 全站共享
  "globalCss": "...",
  "uiState": {...}          // 全站共享
}
```

> 为什么把 `tokens/globalCss` 提到页级之外：它们是"站点级"的东西，
> 放进每页会导致改一次主色要改 N 遍（正好和变量系统的初衷相反）。

### 迁移（无感，复用变量系统那套思路）

`SCHEMA_VERSION` 2 → 3：

- 读 v2 时，把整个 `scene` 包成 `pages: [{ id: 'p_default', name: '首页', path: 'index.html', root: scene.root }]`，
  其余字段（tokens/quickCss/globalCss/uiState）原样上提
- **写回时仍写 v3**；但保留 `root` 字段作为"当前页的镜像"，让老版本程序打开时至少能看到首页
  （老程序会忽略 `pages`，用 `root` 渲染 → 不至于打不开）
- 这是"**前向兼容优先**"策略：宁可多存一份镜像，也不要让用户用旧版打不开新文件

### 分步实施

1. **类型与读写层**：`SceneGraph` 增加可选 `pages`/`activePageId`；`readProject` 做 v2→v3 迁移；
   `writeProject` 写 v3 + `root` 镜像。**此时 UI 不变**（仍只显示首页），先保证"存了再读不丢"
2. **页签 UI**：画布上方（工具栏下）加一条页面栏：`首页 | 关于 | ＋`，可双击改名、右键删除
3. **场景操作隔离**：`useScene` 的所有写操作作用于 `pages[activePageId].root`；
   切页 = 换 root + 清撤销栈（撤销不该跨页）
4. **导出**：多页时导出成一个目录（`index.html` + `about.html` + `assets/`），
   页面间链接用 `path` 字段；单页时行为完全不变
5. **探针**：见下

### 探针（必须覆盖迁移）

- 造一个 v2 工程 → 打开 → 应自动变成 1 页，且 `root` 内容一字不差
- 加第二页 → 保存 → 重开 → 两页都在，各自 root 不串
- 切页后撤销栈被清空（不能撤到另一页的操作）
- 导出多页 → 目录里有两个 html，且 `assets/` 被两页共享（不重复打包）
- **老版本兼容**：手工把 v3 的 `pages` 删掉、只留 `root` → 仍能打开（模拟旧程序读新文件）

### 风险

这是**唯一会改工程格式**的一项。必须满足：

- 迁移是**单向可逆**的（v3 → 删 `pages` → v2 仍可读）
- 每一步都能单独提交、单独回滚
- 在动 UI 之前，先把"读写 + 迁移 + 探针"做扎实

**建议排期：至少 2 轮**（第 1 轮做类型/读写/迁移 + 探针，第 2 轮做页签 UI + 导出）。

## 三、更新器跨平台（需要真机）

Windows 的替换流程（robocopy）已在用；macOS / Linux 走 rsync（兜底 tar）但**从未真机验证**。

需要一台 macOS 与一台 Linux 上做：

1. 打一个旧版本包 → 装好
2. 用新版包触发更新
3. 确认：程序替换成功、`data/` 未被碰、重启后版本号正确、日志里没有报错

在拿到真机之前，这部分**只能标注"未验证"**，不该算完成。
