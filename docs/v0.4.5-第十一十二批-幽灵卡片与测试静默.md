## 一、幽灵卡片：快捷助手样式被隐藏时的占位（第 11 批）

**背景**：把「快捷助手 → 是否显示到下方 CSS 属性」关掉后，快捷助手代管的属性
（`display:flex`、`gap`、`background-image`、`-webkit-text-fill-color`…）会从下面的列表里整块消失。
问题是**它们其实还在生效** —— 用户看到"列表是空的"，就以为这个元素没有样式，
于是反复去「+ 添加属性」重写一遍。

**现在**：只在「开关关着 **且** 这个元素确实有代管样式」时出现一张灰底虚线卡片：

- 一句话说清"这个元素有 N 条样式由快捷助手管理，当前设置为不显示（样式依然生效）"；
- 两个出口：「显示出来」（放回列表并把开关拨回开）、「去快捷助手」（直接改这些样式）；
- 元素没有任何代管样式时不出现（不做无意义噪音）。

探针 `probe-v045-ghostcard.mjs`：开关开→无卡片；关→卡片出现且两个按钮在；
点「显示出来」→卡片消失、属性回列表、开关回开；再关→卡片重新出现；
无代管样式的元素→不出现。

## 二、深色模式：把"硬编码浅色"收敛到语义变量（第 11 批）

原来 `html[data-bc-dark]` 分支散在 12 个 CSS 分片里、约 35 条，各自写死
`#475569` / `rgba(255,255,255,.06)` / `#052e16` 这类值。

现在统一收到 `styles/29-v045-perf.css` 的「深色」一节，**能走语义变量的全走语义变量**
（`--surface-1/2`、`--line(-strong)`、`--text-1/2/3`、`--danger*`），
只保留两类必须"仅深色"的：

1. 半透明遮罩（`cp-backdrop` / `hc-backdrop`）—— 深色下要更暗；
2. 许可证徽章（免费绿 / 受限黄）—— 颜色本身就是语义。

探针断言：该文件里 28 条深色规则**没有任何硬编码 6 位色值**（除上述两类），
并且切到 `data-bc-dark` 时 `--surface-0` / `--text-1` 确实整体换了一套。

## 三、测试窗口**不再抢桌面焦点**（第 12 批 · 用户明确要求）

**用户原话**：「我在干别的事情的时候总会弹出 BlockCanvas 的窗口，很烦……
要么默认折叠只留任务栏图标（但我不知道会不会影响截图），要么新开的窗口不要是整个桌面的『焦点』。
可以给所有的脚本都做一下这个操作。」

### 为什么不用"折叠/最小化"

最小化会让 Chromium 认为页面不可见：`requestAnimationFrame` 与 CSS 动画被节流，
`page.screenshot()` 可能拿到空白帧 —— 探针会莫名其妙变红。所以**不折叠**。

### 采用方案：显示但不激活

| 层 | 做法 |
| --- | --- |
| 主进程 | 带 `BC_NO_FOCUS=1` 启动时，窗口用 `show: false` 创建；`ready-to-show` 后调 `showInactive()`（系统级"显示但不抢前台焦点"），并用 `did-finish-load` 兜底补一次 |
| 脚本 | `tests/e2e/quiet-window.mjs` 提供 `QUIET_ENV` 与 `quietWindow(app)`；**62 个测试/截图脚本**的 launch env 已统一加上该开关 |
| 效果 | 窗口照常渲染、照常能截图、任务栏有图标，但**不会把你正在用的窗口顶掉** |

开关只影响"窗口怎么显示"，不改变任何业务逻辑；正常双击启动（没有这个环境变量）行为完全不变。

验证：`probe-home`（31/31）、`probe-ui-overflow`（0 处问题）、`probe-v045-batch8`（28/28）、
`probe-table`（90/90，含 6 张截图）、`probe-v045-perf-anim`（14/14）、
`probe-input-focus`（16/16）、`probe-v045-ghostcard`（11/11）在安静启动下全部通过 ——
说明截图与焦点相关逻辑都没受影响。

## 四、探针运行器（第 11 批）

`pnpm test:probe` 以前是几十个 `node a.mjs && node b.mjs && …` 串起来：**一个失败就全停**，
后面几十个根本没跑；而且 Windows 上偶发 exit 2（上一条 Electron 刚退出、临时目录还锁着），
看起来像产品坏了。

现在换成 `tests/e2e/run-probes.mjs`：

- 逐个跑、**全部跑完**再汇总（不再中途放弃）；
- 非 0 退出**重试一次**，重试通过标 `PASS*`（诚实标注"重试过"，不是静默吞掉）；
- 两次都失败才算 FAIL，并打印该探针最后 25 行输出；
- 末尾给汇总表（每项 `通过数/总数` + 耗时）+ 总耗时，失败时退出码 1；
- `pnpm test:probe` = 带重试；`pnpm test:probe:once` = 不重试（排查真问题用）；
  `node tests/e2e/run-probes.mjs batch8` = 只跑名字含 batch8 的。

最近一次全量：**49 个探针，49 通过 / 0 失败**，总耗时约 9 分钟。

## 五、顺手修掉一条"假稳定"的旧断言

`probe-help` 的「点目录能跳到对应章节」以前在**全量串跑**时偶发失败（`0 → 0`，单跑必过）。
查下来不是时序问题，而是**断言选错了目标**：

- 它点的是「技术栈 / 目录结构」这种**靠前的章节** —— 目标本来就在视口顶部附近，
  `scrollTop` 几乎不变，"必须变大"自然不成立；
- 顺带还有"只 sleep 700ms 就读一次 scrollTop"的问题（平滑滚动没走完）。

现在：点目录里最后一节（实测是「AI 使用说明」，从顶部跳过去位移约 200px），
并 `waitForFunction` 等 `scrollTop` 增长 ≥200px。连跑 3 次全过。
（这条属于**探针写错**，不是功能坏 —— 如实标注，没有偷偷放宽。）
