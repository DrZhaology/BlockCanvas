# BlockCanvas · 工程文件格式技术分析（JSON 的取舍与演进路线）

> 问题：现在很多东西用 JSON 存（`.bcproj`、快照、`session.json`、`tasks.json`、扩展 manifest），
> 有什么优缺点 / 局限性？有没有更合适的内部文件格式？
>
> 本文先给**实测数据**，再给**结论与路线**。所有数字都是在本仓库 `data/` 上真跑出来的。

---

## 一、现在到底存了什么（实测）

### 1.1 文件清单

| 文件 | 内容 | 写入时机 | 实测大小 |
|---|---|---|---|
| `data/projects/<名>.bcproj` | 完整工程（scene 树 + meta） | 用户 Ctrl+S / 自动保存 | 2.3 KB / **16.5 KB** |
| `data/backups/<项目>/autosave.bcproj` | 最新快照 | 每个备份周期 | 3.3 KB |
| `data/backups/<项目>/snapshot-<时间戳>.bcproj` | 轮转快照（保留 15 份） | 同上 | 3.3–3.6 KB ×8 |
| `data/session.json` | **所有打开标签页的整棵场景** | 场景变化后 **400ms 防抖** | 2.8 KB（1 个空标签） |
| `data/tasks.json` | 后台下载任务记录 | 任务状态变化 | 2 B |
| `data/config.json` | 用户偏好 | 改设置 | 206 B |
| `data/extensions/**/manifest.json` | 插件 / 资源包元数据 | 安装时 | ≤ 4 KB |

### 1.2 格式定义（`.bcproj`）

```jsonc
{
  "format": "BlockCanvas-Project",
  "version": "1.0.0",              // ⚠ 写死的常量，载入端**从不校验**
  "name": "现代产品落地页",
  "updatedAt": "2026-10-11T13:39:40.552Z",
  "meta": { "elementCount": 27 },
  "scene": { "root": { ... } }     // 递归树：id / type / text / attrs / style / children
}
```

写入方式：`JSON.stringify(payload, null, 2)` —— **美化输出**。

### 1.3 关键实测数字（27 个元素的真实工程）

| 形态 | 大小 | 每元素 |
|---|---|---|
| 美化 JSON（现状） | 16,499 B | **611 B** |
| 紧凑 JSON（去掉缩进） | 7,874 B | 292 B |
| 紧凑 + gzip | **2,250 B** | **83 B** |

> 结论：**缩进白占了 52% 的体积**；gzip 还能再压 3.5 倍（相对紧凑）。
> 也就是说 —— 同样的内容，现在落盘的大小是"理论上能做到"的 **7.3 倍**。

### 1.4 一个做对了的地方

**图片不进 JSON**：`<img>` 存的是路径 / URL（`bc-img://` 协议按需读盘），不是 base64。
所以 JSON 只承载"结构 + 样式字符串"，没有被二进制污染 —— 这是本方案能一直撑住的前提。

## 二、JSON 的优点（在这个项目里**真实成立**的部分）

1. **人可读、可手改**：用户把 `.bcproj` 发过来，我能直接看出问题；用户也能自己改一行救回工程。
2. **可 diff**：配上 git / 任意对比工具，"这个版本和上个版本差在哪"一目了然。
3. **零依赖**：Node / 浏览器原生 `JSON.parse`，没有二进制兼容问题、没有版本升级炸裂风险。
4. **天然前向兼容**：加字段 → 旧文件照样读（缺字段就是 undefined，不是报错）。
5. **插件生态友好**：任何语言都能生成/消费 `.bcproj`，第三方扩展门槛极低。
6. **调试成本≈0**：出问题时打开文件就是答案，不需要专门的解析工具。
7. **非常适合"小文件 + 低频写"** —— 而 27 个元素的工程确实属于这一类。

**这些优点不是"聊胜于无"，而是本项目的核心资产**（用户能自救、插件能参与、AI 能直接读）。
所以下面的讨论都建立在"**不要丢掉可读性**"这个前提上。

---

## 三、缺点与局限（逐条对应到本项目的**真实**痛点）

### 3.1 体积冗余（已在流血）
- 每个元素都要重复写 `"id"` `"type"` `"text"` `"attrs"` `"style"` `"children"` 这些键名；
- 加上 `null, 2` 美化 → **实测多花 52%**；
- 一屏 27 个元素就是 16.5 KB，其中真正"信息"的部分只有 2.2 KB（gzip 后）。

### 3.2 没有随机访问 —— 读一个元素也要 parse 整棵树
- 打开工程、切标签、生成图层树、统计元素数，全都要先 `JSON.parse` 整个文件；
- 复杂度 **O(文件大小)**，不是 O(你要的东西)。

### 3.3 写入**永远是全量** —— 这是最贵的一条
| 场景 | 现在怎么写的 | 代价 |
|---|---|---|
| 自动保存 | 整棵 scene 重新序列化 | O(文档大小) |
| 每次备份 | **写两份全量**（`autosave.bcproj` + `snapshot-*.bcproj`） | O(2×文档大小) |
| `session.json` | **所有打开标签页的整棵场景**，每 400ms 防抖重写 | **O(所有标签总大小)** |

> 也就是说：开着 3 个大页面编辑时，每 400ms 就往磁盘写一次"3 个完整工程"。
> 元素量小的时候无感，一旦上万就变成**卡顿 + 磁盘磨损**。

### 3.4 没有二进制能力
- 现在靠"图片只存路径"绕开了；
- 一旦要做"**把图片嵌进工程**（换机也能带走 / 单文件交付）"，就只能 base64 → **体积 +33%**，且完全不可读。

### 3.5 没有完整性校验，坏一个字节全盘皆输
- JSON 是"全有或全无"：文件被截断 / 半写 → `parse` 抛错 → **整个工程打不开**，无法部分恢复；
- 而快照的价值恰恰是"救急"，此时它自己也不可靠就很尴尬。

### 3.6 **没有版本协商入口**（隐性技术债）
- `version: '1.0.0'` 是写死的字符串，**载入端从不读它**；
- 意味着将来任何结构变更（比如把 `style` 拆成 `styles.desktop`）**没有迁移入口**，
  只能靠"猜着兼容"或"读失败就报错"。

### 3.7 其它（本项目暂未踩到，但要记着）
- **数字精度**：JSON number = IEEE754 double。现在样式值都是字符串（`"16px"`），没踩到；
  将来若存坐标矩阵 / 贝塞尔参数要小心。
- **不支持注释**：配置文件想写"这一项是干嘛的"只能靠约定字段。
- **无并发控制**：两个进程同时写会互相覆盖。目前单实例单进程，安全；将来做协作就不够。

## 四、什么时候会真的痛（容量模型）

按实测的 **611 B/元素（美化）** 外推：

| 文档规模 | 美化 JSON | 紧凑 JSON | 紧凑 + gzip | `session.json`（5 个标签） |
|---|---|---|---|---|
| 27 元素（现状） | 16 KB | 8 KB | 2 KB | 40 KB |
| 500 元素 | 305 KB | 146 KB | 42 KB | 730 KB |
| **5,000 元素** | **3.0 MB** | 1.4 MB | 0.4 MB | **7 MB / 每 400ms** |
| 20,000 元素 | 12.2 MB | 5.8 MB | 1.7 MB | **29 MB / 每 400ms** |

> **分水岭在"几千个元素"**：到那时"每 400ms 重写 session"会变成肉眼可见的卡顿。
> 这不是 JSON 的锅，而是 **"JSON + 全量写 + 美化输出"** 这个组合的锅。

## 五、候选格式对比

| 方案 | 体积 | 可读/可 diff | 随机访问 | 增量写 | 二进制资源 | 依赖 | 迁移成本 | 结论 |
|---|---|---|---|---|---|---|---|---|
| **JSON（现状）** | 大 | ✅ 极好 | ❌ | ❌ | ❌ | 无 | — | 方向对，实现要修 |
| **紧凑 JSON（去缩进）** | 中（-48%） | 🟡 一般 | ❌ | ❌ | ❌ | 无 | **极低** | ✅ 立刻可做 |
| **JSON + gzip 落盘** | 小（-86%） | ❌ 丢 | ❌ | ❌ | ❌ | 无（`zlib` 内置） | 低 | 可作过渡 |
| **MessagePack / CBOR** | 小 | ❌ 丢 | ❌ | ❌ | ✅ | 小 | 中 | ❌ 不推荐（丢了最大优点，收益不如 ZIP） |
| **ZIP 容器**（.docx/.sketch 那套） | 小 | ✅ **解压即文本** | 🟡 资源可单独读 | ❌ | ✅ 原样存 | 无（`zlib` + 已有 `zip.ts`） | 中 | ✅ **推荐目标形态** |
| **SQLite** | 小 | ❌ | ✅ 强 | ✅ 事务 | ✅ BLOB | 原生模块 / `node:sqlite` | 高 | 上万元素再说 |
| **自研二进制** | 最小 | ❌ | ✅ | ✅ | ✅ | 自己维护 | 极高 | ❌ 不值 |

## 六、建议路线（按"什么时候做"排，不推翻现有设计）

### 第 1 步 · 低成本立刻可做（收益最大、风险最低）

| # | 动作 | 收益 |
|---|---|---|
| 1 | **落盘不再美化**：`JSON.stringify(payload)`（去掉 `null, 2`）；另提供「导出可读版」菜单给需要手改的场景 | **立省 ~48%** |
| 2 | **快照去重**：现在一次备份写两份全量（`autosave` + `snapshot`）→ 只保留 `snapshot-*`，`autosave.bcproj` 改为"指针/或干脆不写" | 写入量 **减半** |
| 3 | **快照按内容哈希去重**：内容没变就不写新快照（定时器照跑，文件不涨） | 空转时 **写入归零** |
| 4 | **`session.json` 瘦身**：只存**活动标签**的完整场景；其它标签只存 `filePath` + `isDirty`（切回时从磁盘重载） | 写入量从 O(所有标签) → O(1 个) |
| 5 | **加 `schemaVersion`（整数）并在载入时校验 + 迁移表**：`{ schemaVersion: 2, ... }`，读到 1 就走升级函数 | 给未来所有结构变更**留出口**（现在等于没有） |

> 这 5 条**不改格式本身**，旧文件照样能读，全部是"实现层"的修正。
> 做完之后：同样内容体积 ≈ 现状的 1/2，写入频率大幅下降，且拿到了迁移入口。

### 第 2 步 · 中期目标形态：**ZIP 容器**（推荐）

```
demo.bcproj            ← 其实是个 zip（保留 .bcproj 后缀，双击仍能解压看）
├─ manifest.json       # { schemaVersion, name, elementCount, createdAt, ... }
├─ scene.json          # 紧凑 JSON（解压即读、可 diff、可手改）
└─ assets/             # 图片等二进制**原样**存（不再 base64）
    ├─ logo.png
    └─ hero.jpg
```

**为什么是它：**
- **保住了 JSON 的全部优点**：解压出来就是文本，能读能 diff 能手改；
- **二进制资源不进 JSON**：图片原样存，不做 base64（省 33%），还能单独替换；
- **内置压缩**：zip deflate 免费拿到 ~3× 压缩，不用额外设计；
- **部分读取**：只取 `manifest.json` 就能列出"名称/元素数/缩略图"，不必解 `scene.json`；
- **生态先例**：`.docx` / `.xlsx` / `.sketch` / `.fig` 全是这个套路，用户和工具都熟悉；
- **实现成本可控**：Node 内置 `zlib`，本仓库已经有 `src/main/zip.ts`（自研 zip 读写）。

**向后兼容**：读入时嗅探前 4 字节魔数 `PK\x03\x04` → 是 zip 走新路径，不是就走旧的纯 JSON 路径。
**老文件永远能开**，新文件用新格式。

### 第 3 步 · 只在规模真的上来时才做：**SQLite**
- 触发条件：**单工程 > 2~3 万元素**，或要做"多人协作 / 增量同步 / 局部加载"。
- 那时才值得付出：失去文本可读性 + 原生模块按平台 rebuild（打包复杂度上升）+ 给插件补一套数据库 API。

### 不建议
- **MessagePack / CBOR**：省了体积但**丢掉了可读性与可 diff**（这是本项目最大的资产），
  而压缩效果并不比"紧凑 JSON + gzip / ZIP"更好，迁移成本却不低。
- **自研二进制格式**：维护成本远超收益。

---

## 七、一句话结论

> **JSON 这个方向是对的**（可读、零依赖、插件与 AI 友好），痛点不在"用不用 JSON"，
> 而在三个实现细节：
> **① 美化输出白占一半体积；② 写入永远全量（session 每 400ms、快照每次两份）；③ 没有 `schemaVersion` 这个迁移入口。**
>
> 先修这三件事（第 1 步，不动格式）；再把 `.bcproj` 换成 **ZIP 容器**（第 2 步，保留可读性的同时拿到压缩与二进制能力）；
> **SQLite 留到文档真的上万元素、或要做协作时再上。**

## 附：本分析用到的实测命令

```bash
# 体积 / 每元素成本 / gzip 潜力
node -e "const fs=require('fs'),z=require('zlib');
const f='data/projects/demo-page.bcproj';
const raw=fs.readFileSync(f),o=JSON.parse(raw);
const min=Buffer.from(JSON.stringify(o));
console.log('美化',raw.length,'紧凑',min.length,'gzip',z.gzipSync(min,{level:9}).length,
            '元素',o.meta.elementCount);"

# 快照目录
find data/backups -name "*.bcproj" -printf "%s %p\n" | sort -rn | head
```
