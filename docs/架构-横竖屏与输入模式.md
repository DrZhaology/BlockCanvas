# 横竖屏方案评审：一套代码撑不撑得住

> 结论先给：**不用分两套代码，一套撑得住。**
> 但现在这套写法有个结构性毛病 —— 不是"用 CSS 检测"这件事错了，是**把"窗口宽度"当成三个互不相关的开关在用**。
> 竖屏反复崩，崩的是这个，不是 CSS 本身不行。

本文件基于 v0.4.6 工作区实测数据（2026-11-14）。

---

## 一、先把"耦合有多大"量出来

说"CSS 检测撑不撑得住"之前，得知道到底有多少代码在感知横竖屏。实测：

| 指标 | 实测值 | 位置 |
|---|---|---|
| 渲染层文件总数 | 191 | `src/renderer/**` |
| **直接感知外壳形态的 TS 文件** | **3** | `lib/shellMode.ts`、`App.tsx`、`lib/useEdgeSwipe.ts` |
| 外壳断点定义 | 60 行 | `lib/shellMode.ts`，阈值 900px，单一断点 |
| 横竖屏专用 CSS | 444 行 | `styles/33-v046-shell.css` |
| 其中 `[data-shell='narrow']` 覆盖块 | **51 块** | 同一文件 |
| 按宽度生效的 `@media` | 4 条 | 720 / 720 / 980 / 520 |
| 其余 `@media` | 14 条 | 全是 `prefers-reduced-motion` / `max-height`，与横竖屏无关 |

**结论一：体量上完全撑得住。** 191 个文件里只有 3 个知道横竖屏存在，差异全部收敛在**一个钩子 + 一个 CSS 分片**里。这不是"到处 if 判断"的代码库。

顺带一提，这个分层本身已经是对的方向：

```
场景模型 / 节点渲染 / 表格引擎 / 导出 / 主题
        ↑ 零感知横竖屏（CanvasNode、tableOps、export 里没有一个 narrow 分支）
────────────────────────────────────────────
外壳（面板在左在右、是并排还是抽屉）  ← 全部差异在这层
```

## 二、真正的问题：一个断点当三个开关用

现在 `data-shell='narrow'` 这一个状态，同时决定三件**本质无关**的事：

| 它实际在管什么 | 现在靠什么判断 | 该靠什么判断 |
|---|---|---|
| ① **布局**：面板并排 vs 抽屉 | 窗口宽度 < 900px | 窗口宽度 ✅ **这个用法是对的** |
| ② **输入**：点按目标 ≥44px、边缘滑动开抽屉、长按调位置 | 窗口宽度 < 900px | ❌ **该看设备有没有鼠标/手指** |
| ③ **产品能力**：竖屏不保留多标签页 | 窗口宽度 < 900px | ⚠️ 该是明确的产品决定，不是宽度的副作用 |

问题出在 ②。**宽度不是输入方式的代理。** 全仓实测：`hover: hover`、`pointer: coarse`、`maxTouchPoints` —— **0 处**。也就是说这个应用至今没有任何"我是不是在触摸设备上"的判断。

两个立刻能复现的错配：

- **1280px 的平板**（iPad 横放）：宽度 ≥900 → 判定 `wide` → 面板固定 456px 并排、没有把手、Alt 悬停才出的吸附墙和定界框**在触摸屏上永远调不出来**（没有 Alt 键、没有 hover）。布局判断是对的，交互判断全错。
- **700px 的桌面窄窗**（Windows 上把窗口拖窄）：宽度 <900 → 判定 `narrow` → 给你 44px 触摸目标、装上边缘滑动监听、把手长按 420ms。用鼠标的人会觉得"反应迟钝、要点两下"。

这就是为什么竖屏的 bug 是一类一类复发、而不是一个一个修完。**根因是这个轴混了，不是某个样式写错了。**

> 上一轮修"手指关不掉抽屉"，根因是触摸滚动会派发 `pointercancel` 掐断指针流 —— 那正是"输入方式被当成布局问题处理"的典型症状：代码按窄屏装了手势，却没按输入设备选实现。

## 三、那要不要分两套代码？

**不要。** 理由是可量化的：

- 真正需要不同的，只有**外壳怎么摆**（444 行 CSS）和**手势怎么接**（1 个钩子）。这是 191 个文件里的 4 个。
- 真正不能分成两份的，是**最难的那 90%**：画布渲染、节点树、属性面板、表格引擎、导出、版本兼容。这些东西横屏竖屏**一模一样**。分两套等于把这 90% 复制一份，然后每次都改两遍、两边慢慢漂移。

分两套代码能解决的唯一问题是"改动干扰"，而这个问题的成本是"永久双份维护"。在**同一个产品、同一批功能**的前提下，这个交易永远亏。

---

## 四、建议：改成三段式（仍在同一个代码库）

```
① 核心 core      一份，零分支  场景/渲染/表格/导出/主题
② 外壳 shell     一份 + 布局表  面板摆哪、并排还是抽屉
③ 输入 input     一份 + 适配器  鼠标悬停·Alt  ⇄  手指长按·双指
```

### 4.1 把 `.app` 上的一个属性拆成两个正交属性

```html
<!-- 现在 -->
<div class="app" data-shell="narrow">

<!-- 改后（已落地） -->
<div class="app" data-shell="stack" data-input="touch">
```

- `data-shell`：`split`（并排，≥900px）/ `stack`（堆叠/抽屉）—— **只看宽度**，CSS 管布局。
- `data-input`：`pointer`（有精确指针+悬停）/ `touch`（粗指针、无悬停）—— **只看设备能力**。

> 为什么没叫 `data-layout`：`.workspace[data-layout='left|bottom']` 已经在 8 个样式分片里
> 用了 60 次（表示"元素面板摆左边还是下边"）。同一个属性名挂在两个不同元素、
> 值域还不同，后来人一定会写错选择器 —— 实测写这个方案时就差点踩到。
> 所以布局轴沿用 `data-shell`（只挂 `.app`），只把值从 wide/narrow 换成 split/stack
> （描述**排列方式**而不是**屏幕宽窄**，也更不容易被误当成输入开关）。

值本身的改名不是化妆：`wide/narrow` 是宽度形容词，看着就像"窄屏=另一套交互"；
`split/stack` 只是说"两栏还是叠起来"。改名的同时把 55 处选择器和 3 处探针都过了一遍，
等于强制做了一次审计。

CSS 侧两个选择器各管各的，互不牵连：

```css
/* 布局：只改位置和尺寸 */
.app[data-shell='stack'] .right-pane-wrap { /* 变抽屉 */ }

/* 输入：只改可点区大小和悬停反馈，与布局无关 */
.app[data-input='touch'] .prop-row { min-height: 44px; }
/* 两个条件取并集的地方：小屏幕 或 手指，都需要大目标 */
.app[data-shell='stack'] .toolbar .tb-btn-ghost,
.app[data-input='touch'] .toolbar .tb-btn-ghost { min-height: 44px; }
```

判断来源（`lib/inputMode.ts`，已落地）：

```ts
// 首选：粗指针 + 无悬停 = 手机/平板
const COARSE = '(hover: none) and (pointer: coarse)';
// 兜底：只证明"没有悬停"，再叠加 maxTouchPoints —— 两个都成立才认触摸。
// 只靠 maxTouchPoints 会把带触摸屏的 Windows 笔记本一起判成触摸（那台机器主输入还是鼠标）。
const isTouch = matchMedia(COARSE).matches
  || (navigator.maxTouchPoints > 0 && matchMedia('(hover: none)').matches);
```

订阅两条查询的 `change` 事件（不是 resize），插拔外设 / 翻转模式时即时切换。

### 4.2 布局照旧用 CSS 断点，但方向要翻转

**现在的问题**：`33-v046-shell.css` 里 51 个 `[data-shell='narrow']` 块，几乎每一条都是**把宽屏写法撤销掉**（`display: none`、`position: absolute`、`grid-template-columns: 1fr`、`!important`）。这意味着：

> 每加一个宽屏功能，就欠一笔"窄屏得撤销它"的债。没人写撤销 → 竖屏就崩一块。

竖屏反复崩，就是这个债在滚利息。

**翻转成"加成式"**：基础样式写成**单列即可用**（360px 也不炸），宽屏块只负责"多排两列"。

```css
/* 基础：单列，任何宽度都不炸 */
.elem-pane-wrap { position: fixed; inset-block: 0; inline-size: min(86vw, 320px); }
.right-pane-wrap { /* 同上 */ }

/* 宽屏：只是把两列接回网格 */
.app[data-layout='split'] {
  .elem-pane-wrap  { position: static; inline-size: 230px; }
  .right-pane-wrap { position: static; inline-size: 456px; }
}
```

这样**新功能默认就是竖屏可用的**，宽屏是想加才加。44 行 CSS 换掉 51 块撤销，行数还更少。

### 4.3 输入层收敛成适配器

```ts
// lib/useNodeGesture.ts —— 上层组件只说"要移动这个元素"
// pointer: pointerdown + mousemove 路径
// touch:   pointerdown → 420ms 长按进入移动态；拖动前判定方向，横滑让给手势、竖滑让给滚动
```

组件里不再出现 `if (narrow) 用触摸实现`。

## 五、什么情况下才真的该分两套

给三条判据，只有第 3 条真需要分仓：

| 情形 | 该怎么做 | 分代码库？ |
|---|---|---|
| 竖屏是**同一个编辑器**，只是空间小 | 上面三段式 | ❌ 不分 |
| 竖屏是**另一种产品**（只查看/微调，不做完整编排） | 同核心 + 两个路由入口 + 能力开关 | ❌ 仍不分，只分**功能开关** |
| 上 **原生壳**（Capacitor / RN），要调摄像头、本地文件、原生手势 | 外壳层 + 输入层各一份，核心打成共享包 | ⚠️ 只有这里分，且**核心仍是一份** |

第三种的信号是"需要访问原生能力"，不是"屏幕变窄了"。**屏幕变窄从来不是拆代码库的理由。**

## 六、落到"把竖屏做好"这件事上

按上面的诊断，竖屏剩下的活不是零散修样式，是三步：

1. **拆轴**（约半天）：新建 `inputMode.ts`，`.app` 换成 `data-layout` + `data-input` 双属性，51 块选择器机械改前缀。**行为预期零变化**，验收 = 现有 `probe-shell-narrow` 46 条断言全绿（仅改选择器名字，数值不动）。
2. **翻转 CSS 方向**（约一天）：把 `33-v046-shell.css` 的撤销式覆盖重写成基础单列 + 宽屏加成。验收 = 360 / 500 / 700 / 899 / 901 / 1280 六档宽度下逐屏截图，且新增"宽屏功能不得在窄屏溢出"的探针。
3. **触摸路径补齐**（约一天）：长按/双指/滚动冲突走适配器，`probe-shell-narrow` 增加"模拟触摸设备 + 1280px 宽度"一组断言（此时应**没有抽屉，但点按目标仍 ≥44px**）—— 这一条现在会红，正是要修的东西。

另外有一件**与 CSS 无关**但竖屏迟早要撞的事：画布是**固定设计宽度**的页面预览（`canvasWidth`，可拖拽、`auto`）。竖屏窗口 360px 看一张 1440px 的页面，靠的是 `zoom` 缩放。`measureFixedViewport()` 和 `--bc-fl-*` 那套 fixed 定位框的数学全部建立在 zoom 上，竖屏下 zoom 更小、换算误差被放大 —— 这属于**画布几何**，不是响应式 CSS。要做的是"适配宽度（fit-width）"这个画布功能，别指望媒体查询。

---

## 七、两个产品问题的答案（已定）

1. **竖屏定位**：完整的编辑器，只是空间小 → 三步全做，横竖屏能力对等。
2. **触摸设备**：要支持（平板会真的打开 Web 版）→ 输入轴必须建起来，不能只做"鼠标也能完成操作"。

### 新增验收网

`tests/e2e/probe-shell-widths.mjs`（**87 条**）—— 这是"加宽屏功能别再崩窄屏"的网：

- 六档宽度 **360 / 500 / 700 / 898 / 902 / 1280**，每档断言：外壳形态、输入轴不被宽度带跑、页面无横向滚动、无元素越界、画布可编辑区 >120px、画布高 ≥240px、工具栏有高度、面板形态（覆盖层 vs 相对定位）、把手数量、网格行列、工作区高度无多余空行。
- 断点边界 **898 ↔ 902** 专项：形态整体翻转、把手一起出现/消失。
  > 为什么不是 899/901：实测 `setContentSize` 会把视口宽吸附到偶数（899→900、901→900），奇数值设不出来，硬测会得到"正好压在断点上"的假结果。
- **输入轴独立性**（拆轴之前做不到的验收）：用 CDP `Emulation.setTouchEmulationEnabled` + `setEmulatedMedia` 把设备模拟成触摸，**窗口仍保持 1280px**，断言：
  - `data-input` 切成 `touch`（宽度没变，输入变了）
  - 布局仍是 `split`、**没有抽屉把手**（输入轴不会把布局带跑）
  - 工具栏主按钮 ≥44×44
  - 关掉模拟后 `data-input` 自己切回 `pointer`、按钮回到 <44px（订阅是活的，不是启动时判一次）
  > 踩坑：只把 media features 改回 `hover/hover + pointer/fine` 切不回来 ——
  > Chromium 在 touch 模拟开启时仍按 `coarse` 报，必须同时 `setTouchEmulationEnabled(false)`。

- **② 的其余层次**：元素面板内部（抽屉里竖排）、工具栏两行、首页/设置页/项目中心单列、标题栏紧凑 —— 这些目前仍是带 `data-shell='stack'` 前缀的覆盖块。功能是对的（探针全绿），但还没翻成"基础 + 宽屏加成"的写法。

- **④ 竖屏逐屏打磨 / ⑤ 画布 fit-width**：未开始。
