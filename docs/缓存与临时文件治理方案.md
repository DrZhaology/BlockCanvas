# BlockCanvas · 缓存与临时文件治理方案

> 用途：回答"程序运行时往 Temp 写了很多文件、而且不会自动删"这个问题。
> 本文分四部分：**① 实测现状 → ② 治理方案 → ③ Temp 能不能全部放进程序文件夹（结论）→ ④ 实施进度与清单**。
> 状态：**第 1 批已实施**（设置页分类管理 + 启动清理临时文件 + 统计口径修正，v0.4.4）；
> 集中化到 `data/tmp/` 与脚本自删排到下一批。

---

## 一、实测现状（2026-10-16 在本机真实取样）

### 1.1 三类"会写盘"的地方，性质完全不同

| 类别 | 位置 | 谁负责清 | 现状 |
|---|---|---|---|
| **A. 程序自己的数据区** | `<程序目录>/data/` | 我们 | ✅ 可控：已有目录结构 + 启动自动清洁 |
| **B. 系统临时目录** | `%TEMP%` / `$TMPDIR` / `/tmp` | **操作系统的"磁盘清理"，不是我们** | ❌ **就是用户抱怨的地方** |
| **C. Chromium 运行时缓存** | `<程序目录>/data/user-data/` | 我们 | 🟡 已有清理入口，但覆盖不全 |

> 好消息：**C 类已经被关进了 `data/user-data/`**（`initDataDirectories()` 里 `app.setPath('userData', …)`），
> 没有污染系统的 `%APPDATA%\BlockCanvas`。这一点之前做对了。
> 坏消息：**B 类完全没管**。

### 1.2 实测：Temp 里到底残留了什么

```
%TEMP%\bc-preview-1791685056189.html     1.9 KB   10-11 10:17
%TEMP%\bc-preview-1791685063068.html     1.9 KB   10-11 10:17
%TEMP%\bc-preview-1791703777550.html    12.8 KB   10-11 15:29
%TEMP%\bc-preview-1791724437766.html   102.4 KB   10-11 21:13
%TEMP%\bc-preview-1792148105550.html     1.1 KB   10-16 18:55
…（共 10 个，最早的是 5 天前）

%TEMP%\bc-updater-mv3wffgp\apply-update.bat     1.3 KB
%TEMP%\bc-updater-mv3wffgp\rename-folder.ps1    0.9 KB
%TEMP%\bc-updater-xxxx\…                        （共 2 个目录）
```

### 1.3 两个"元凶"的代码位置与根因

**① 浏览器预览 —— `src/main/main.ts` → `ipcMain.handle('preview:open')`**

```ts
const file = join(app.getPath('temp'), `bc-preview-${Date.now()}.html`);
writeFileSync(file, html, 'utf-8');
await shell.openPath(file);
```

- 文件名带 `Date.now()` → **每预览一次就新增一个文件**，永不覆盖、永不删除。
- 为什么必须落盘？因为要交给**系统默认浏览器**打开，不能是内存数据（`data:` URL 在部分浏览器会被拦、也不便于相对资源）。

**② 自动更新脚本 —— `src/main/updater.ts` → `finishUpdateFromZip()` + `writeWindowsScript()`**

```ts
const workDir = join(app.getPath('temp'), `bc-updater-${Date.now().toString(36)}`);
```

生成 `apply-update.bat`（Windows）/ `apply-update.sh`（macOS/Linux）+ `rename-folder.ps1`。
脚本最后一行本来写了 `del "%~f0"` 想自删，但：

```bat
'start "" "%TARGET%\\' + exeName + '"',
'exit /b 0',
'del "%~f0"'          ← 永远执行不到（前面已经 exit 了）
```

- `del "%~f0"` 写在 `exit /b 0` **之后** → 死代码；
- `rename-folder.ps1` 从来没被删过；
- `bc-updater-*` **目录本身**也没有任何人删；
- 失败路径有 `rmSync(workDir)`，**成功路径没有** → 每次成功更新留一份。

> 为什么更新脚本必须落盘？因为它要在**主进程退出之后**、由一个独立进程执行（要替换正在运行的程序本体），
> 所以不能是内存里的字符串。

### 1.4 其它"会慢慢变大"但还没失控的地方

| 位置 | 现状 | 备注 |
|---|---|---|
| `data/downloads/` | 0 B（当前） | 用户每点一次「下载 zip」就多一个包，**没有清理策略** |
| `data/user-data/` | 18 MB | Chromium profile：Cache / Code Cache / GPUCache / blob_storage 可清；**Local Storage / Preferences / Session Storage 不能清**（那是界面偏好与会话） |
| `data/backups/` | 44 KB | 按项目隔离的快照，已有 `clearOrphanBackups()` |
| `<exe 旁>/debug.log` | 19 KB | Chromium 日志，运行期写在 exe 旁边 |
| `<安装目录>/.update/` | 更新时出现 | 脚本里有 `rmdir /s /q`，但**更新中途失败**会残留 |

### 1.5 一句话总结

> **不是"程序在乱写"，而是"程序写的每一处都没有人负责收尾"。**
> 三类文件各有各的合理理由必须落盘，缺的是**统一位置 + 明确生命周期 + 启动时自愈**。

## 二、治理方案（四层，从"不该产生"到"必须产生也要管好"）

### L0 · 能不落盘就不落盘

| 场景 | 现在 | 改法 |
|---|---|---|
| 浏览器预览 | 每次新文件名 | **固定文件名** `preview.html`（同一目录覆盖写）→ 数量恒定 = 1，不再增长 |

> 更新脚本无法避免落盘（要脱离主进程执行），只能靠 L1/L2 管。

### L1 · 集中化：程序产生的临时文件，一律进 `data/tmp/`

```
data/
├── tmp/                    ← 新增：程序自己的临时区（可一键清空、可启动自愈）
│   ├── preview/            ← 浏览器预览 HTML（保留最近 5 个）
│   └── updater/            ← 更新脚本工作目录（脚本执行完自删）
├── downloads/              ← 用户下载的更新包（保留策略见 L3）
├── user-data/              ← Chromium profile
└── …
```

**为什么不再用系统 Temp**：

1. **可解释**——用户在「设置 → 存储」里能看到它、能自己删；系统 Temp 他根本不知道在哪；
2. **可自愈**——启动时清理自己目录**零风险**；扫系统 Temp 永远有"误删别人文件"的顾虑；
3. **便携版一致性**——"删掉 `data/` 就回到出厂状态"这条承诺才成立。

> 保留一个例外：`app.getPath('temp')` 仍可作为**兜底**（`data/tmp` 不可写时，例如程序放在只读盘）。

### L2 · 生命周期：谁创建，谁负责收尾

| 文件 | 收尾方式 |
|---|---|
| `data/tmp/preview/preview.html` | 固定名覆盖写；启动时只保留最近 5 个（如果改成带时间戳的话） |
| `data/tmp/updater/<id>/` | **脚本自己删自己**：Windows 用 `rmdir /s /q "%~dp0"` 放在 `exit` **之前**（或 `start /b cmd /c "ping -n 3 127.0.0.1 >nul & rmdir /s /q ..."` 延迟删）；POSIX 已是 `rm -f "$0"`，补上删目录 |
| `<安装目录>/.update/` | 成功/失败两条路径都清（失败时由主进程 `rmSync`） |
| `debug.log` | 启动时若 > 1 MB 直接删；或 `app.commandLine` 关掉日志落盘 |

### L3 · 自动清理：扩展现有 `clearAppCache()`（启动时 + 手动按钮）

现有 `clearAppCache()` 已经清了 `data/user-data/` 下的 Cache 系列。
下一轮把它扩成**统一的"存储自愈"**：

```
clearAppCache()  ──┬─ Chromium 缓存（已有：Cache / Code Cache / GPUCache / Dawn* / blob_storage）
                   ├─ data/tmp/**            全清（保留最近 N 个 preview）
                   ├─ data/downloads/**      超过 30 天 或 超过 500 MB 的旧包（**保留最近一次**）
                   ├─ <安装目录>/.update/    残留的更新暂存
                   └─ 历史遗留迁移清理：系统 Temp 里前缀为 bc-preview-* / bc-updater-* 的旧文件
                                             （**只按我们自己的前缀匹配，绝不扫全目录**）
```

配套：
- 「设置 → 存储与缓存管理」已有占用统计，**按上面四类分别显示**（用户能看懂"这 18 MB 是什么"）；
- 每类后面一个「清理」按钮 + 顶部一个「全部清理」；
- 现有两个开关（`autoCleanCacheOnStartup` / `autoCleanOrphansOnStartup`）保留，再加一个
  `autoCleanTempOnStartup`（默认**开**）。

### L4 · 防呆：给"增长型"目录加预算

- 任何"写进去就不删"的目录，都要有一个**上限**（文件数或字节数），超了按时间淘汰。
- 已落地的先例：`history.past` 上限 200 条、快照按项目隔离。
- 下一轮把这条规则补到：`data/tmp/`、`data/downloads/`、`data/backups/<项目>/`（保留最近 N 份快照）。

### 安全红线（三条，写进代码注释）

1. **绝不递归清空系统 Temp 目录本身**，只按前缀匹配删我们自己的文件；
2. **绝不删 `data/user-data/` 下的 `Local Storage` / `Preferences` / `Session Storage` / `Network`** ——
   那是界面偏好与会话，不是缓存；
3. 清理前先 `statSync` 判断**是不是目录 / 是不是我们创建的**，且**单次删除有上限**（沿用项目的"小批量"习惯）。

## 三、Temp 能不能全部放进程序文件夹？

**结论：能，只有一样东西不建议放。**

按"谁产生的"分三类看：

| # | 谁写的 | 能不能放程序目录 | 怎么做 / 为什么 |
|---|---|---|---|
| 1 | **程序自己写的临时文件**<br>（浏览器预览 HTML、更新包解压暂存） | ✅ **完全可以，而且推荐** | 直接写 `data/tmp/`。好处：用户看得见、能自己删、启动自愈零风险、便携版"删 `data/` 就干净"这条承诺才成立 |
| 2 | **Chromium 内核自己的临时文件**<br>（崩溃转储、着色器缓存、内核下载暂存…） | ✅ **可以** | `app.setPath('temp', join(dataRoot(), 'tmp', 'system'))`，**必须在 `app.whenReady()` 之前调用**才生效；目录不可写时用 `resolveWritableDir()` 回退到系统 Temp |
| 3 | **自动更新的替换脚本** | ❌ **不建议** | 见下方"唯一例外" |

### 唯一例外：更新替换脚本为什么必须留在系统 Temp

脚本执行期间，程序文件夹会被**改名**（`BlockCanvas` → `BlockCanvas-v0.4.4`）。如果脚本自己就待在这个文件夹里：

- Windows 的 `%~f0` / POSIX 的 `$0`（脚本自我引用）会**立刻失效**；
- 脚本还要 `rmdir` 掉 `<安装目录>/.update/`，而 `.update/` 就在被改名的目录里；
- 脚本必须"活过"程序退出与目录改名这两个事件。

所以它只能待在**程序目录之外**。折中做法是"留在系统 Temp，但**执行完把自己删干净**"——
这正是第 1.3 节里那个 `del "%~f0"` 死代码要修的地方。

### 顺带说明：为什么当初把 `userData` 搬进 `data/`

`app.setPath('userData', <data>/user-data)` 已经在做了，所以 Chromium 的 **profile**（缓存 + 界面偏好 + 会话）
本来就在程序目录里 —— 系统 `%APPDATA%` 早就没被污染。剩下的只有"**系统 Temp**"这一块，
而它正好就是第 1、2、3 类里能搬的那两类 + 一个不能搬的例外。

### 搬进程序目录的代价（要不要做，你决定）

| 代价 | 说明 |
|---|---|
| 目录不可写 | 装在 `/Applications`（macOS）或只读盘 → 必须回退到用户目录（已实现 `resolveWritableDir`） |
| Linux `noexec` | `/tmp` 常挂 `noexec`，程序目录也可能在 `noexec` 挂载点 → 脚本类文件执行会失败（这也是"更新脚本别放程序目录"的第二个理由） |
| 性能 | 放 U 盘 / 网络盘时，临时文件读写会变慢（Chromium 缓存尤其明显） |
| 杀软 | 程序目录通常被实时扫描，临时文件写入更容易被拦（表现为"偶发卡顿"） |

## 附：为什么不做"完全不落盘"

| 场景 | 能否不落盘 | 原因 |
|---|---|---|
| 浏览器预览 | ❌ 不能（但可固定名） | 必须交给系统默认浏览器打开；`data:`/`blob:` URL 在部分浏览器被拦，且相对资源解析受限 |
| 更新脚本 | ❌ 不能 | 要在主进程退出后由独立进程执行（替换正在运行的程序本体） |
| 解压更新包 | ❌ 不能 | 目标就是磁盘上的程序目录 |
| Chromium 缓存 | ❌ 不能 | 浏览器内核行为，只能"关进 data/ + 定期清" |
| 导出 HTML | ✅ 本来就不落临时盘 | 直接写用户选的路径 |

结论：**该落盘的落盘，但必须"集中、有名、有主、能自清"** —— 这就是本方案的全部要点。
