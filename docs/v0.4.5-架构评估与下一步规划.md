### 1.3 三个关键结构事实（后面所有结论都基于它们）

**事实 A：渲染层零 Node/Electron 依赖。**
对 `src/renderer/**` 全量搜索 `require('fs'|'path'|'child_process'|'electron')`、
`from 'node:*'`、`from 'electron'` —— **命中 0 个文件**。
所有系统能力都走 `window.bc.*` 这一个接口（preload 暴露约 **74** 个方法，
渲染层 **133** 处调用，主进程注册 **65** 个 IPC 通道）。

**事实 B：主窗口被硬锁在 ≥960px。**
`src/main/main.ts` 的 BrowserWindow 选项：`width: 1280, height: 800, minWidth: 960, minHeight: 640`。
配合事实 C —— **编辑器外壳不可能被压到手机宽度**。

**事实 C：外壳几乎没有窄屏适配。**
全项目 `@media (max-width: …)` 只有 **3 条**（`720px` ×2、`980px` ×1）。
`BREAKPOINTS = ['desktop','tablet','mobile']`（768 / 480）只作用于**被设计的那张网页**
（画布内容），**不作用于编辑器自己的界面**。

> 结论：**"手机端的编辑器界面"目前是完全不存在的状态**，不是"做得不好"。

## 2. 三个问题的分析

### 2.1 现有架构能不能撑住代码量继续涨？

#### 结论

**分层架构能撑；组件层的文件粒度撑不住。**

#### 撑得住的部分

1. **渲染层是纯 Web 应用**（事实 A）。这是最值钱的设计决策 ——
   它同时解决了"未来换宿主"（网页版、安卓）和"渲染逻辑可测试"两件事。
2. **数据层与视图层分离干净**。`SceneElement` 是纯数据（`style` / `attrs` / `children` /
   `responsive` / `pseudoStyles`），画布渲染器与导出器读同一份数据、共用
   `lib/styleClass` 的同一套规则文本 → "画布所见 = 导出所得"天然成立。
3. **主进程只 5,490 行**，且都是文件/网络/系统这类边界清晰的活，不会成为瓶颈。
4. **`lib/` 是健康的**：39 个文件 6,213 行，职责单一，能被探针独立验证。

#### 撑不住的部分

**① 单文件 2000+ 行的"上帝组件"（最大技术债）**

`Canvas.tsx` 2,431 行里同时装着：Alt 手势全家桶（拖拽/缩放/吸附/盒模型）、
选区与合并外框、缩放锚点、媒体渲染分支、就地文本编辑、覆盖层定位。
`Inspector.tsx` 2,367 行同理（属性行、各专属编辑器分发、中键定位、快捷助手）。

**这不是猜测，v0.4.5 一轮里就在这些文件上连续踩坑**：
- 重复声明 `zoomRef`（快 2,400 行的文件里已有同名变量）；
- 把音频渲染分支错放进 `SELF_CLOSING_TAGS` 块（`audio` 并不在那个集合里）→ 整段是死代码、永不执行；
- 改 `commonProps` 结构时把 `className` 弄成重复键。

症状的本质：**2,000 行文件的"局部修改半径"超过了一次能装下的工作记忆。**

**② CSS 是"按批次命名"而不是"按域命名"**

`13-polish-v040` / `23-v044d-ui` / `28-v045-zindex` —— 名字回答的是"哪一批加的"，
不是"管什么"。后果本轮真实发生：同一条中键搜索样式散在 `23`、`24`、`27`、`28` 四个文件里，
改完 `28` 忘了 `27` 还留着旧的 `inset 2px 0 0` 蓝色竖线，
最后靠"断言时排除注释行"才勉强把探针写对。

**③ `main.ts` 既是窗口管理又是 65 个 IPC 注册 + 菜单 + 导出 + 更新入口**（1,633 行，正在往 2,000 走）

**④ `sceneStore.ts` 1,618 行**：选择器、结构变更、样式变更、历史栈混在一个文件，
导致只能用 E2E 验证，写不了单测。

#### 拆分方案（判定标准：单文件 ≤600 行；纯逻辑可单测）

```
components/canvas/
  Canvas.tsx        组装 + 缩放/平移（≤500）
  CanvasNode.tsx    单节点渲染（含 img/video/audio 分支分离）
  drag.ts           Alt 手势：move/resize/font 三种模式（纯函数化，可单测）
  walls.ts          墙与吸附计算（纯函数）
  boxModel.ts       盒模型测量（纯函数）
  marquee.ts        框选
components/inspector/
  Inspector.tsx     页签与组装（≤400）
  ElementPropsBody.tsx
  PropertyRow.tsx
  editors/          ColorField / NumberUnit / Trbl / Border / Transform / Gradient…
store/scene/
  selectors.ts
  style.ts          样式变更（含偏移钳制等规则）
  structure.ts      结构变更
  history.ts
main/ipc/
  project.ts / assets.ts / update.ts / storage.ts / extensions.ts
styles/            （按域重组，同一组件只允许一个文件里有规则）
  theme.css / shell.css / canvas.css / inspector.css / overlay.css
  empty-home.css / projects.css / settings.css / table.css / help.css
```

`Icon.tsx`（924 行）：改为由 `assets/icons/*.svg` 构建时自动生成映射表，加图标不改代码。

#### 什么时候必须做

**不是"代码量到多少行才做"，而是"下一个大功能之前"**。
理由是：这些文件正是下一轮要动的（fixed 空气墙在 `drag.ts/walls.ts`、
手机外壳在 `shell.css`、多页工程要动 `sceneStore`）。
**先拆再改，比在 2,400 行文件里改完再拆便宜得多。**

### 2.2 适配安卓 + 打包成单文件 HTML

#### 2.2.1 安卓：三条路线，只有一条现实

Electron **官方不支持 Android**，也没有可行社区方案（架构是"打包 Chromium + Node"，安卓上跑不动）。

| 路线 | 做法 | 渲染层复用度 | 评价 |
| --- | --- | --- | --- |
| **A. Capacitor（唯一推荐）** | 渲染层当纯 Web 应用，套 Android WebView 壳；`window.bc.*` 用插件重写 | **接近 100%** | 最现实 |
| B. Tauri Mobile | Rust 壳 + WebView | 渲染层可复用，主进程 5,490 行要重写 | 生态未成熟 |
| C. React Native | 完全重写 UI | ≈0 | 不现实 |

**为什么 A 对本项目格外合适**：事实 A（渲染层零 Node 依赖）意味着
`src/renderer/**` 整体可搬，只需为那 **74 个方法**写一套 Android 实现：

| 能力 | Android 对应实现 |
| --- | --- |
| 工程文件读写（`.bcproj`） | SAF（Storage Access Framework）/ Capacitor Filesystem |
| zip 打包与解包 | **可复用**：`src/main/zip.ts` 是纯 zlib 逻辑，可下沉到共享层 |
| 素材与缩略图 | 本地文件系统 + Canvas 生成 |
| 更新 | 换成 APK 自更新 / 应用商店（现有更新器不适用） |
| 系统对话框 | Capacitor Dialog |
| 便携数据区 `data/` | **概念冲突**，安卓 scoped storage 下不成立，需重新设计落点 |

**必须正视的三个安卓难点**：

1. **触屏没有 Alt / 中键 / 悬停**。本项目的交互体系重度依赖这三样
   （Alt 手势、中键搜索、Alt 悬停盒模型）。安卓上必须做替代映射
   （长按 = Alt、双指 = 中键…）—— 这是**交互范式的重新设计**，不是移植。
2. **性能**：画布组件大量使用 `getBoundingClientRect` 做测量，移动 GPU 上要重新压测。
3. **外壳布局不存在**（事实 B + C）：编辑器的手机界面要从零做。

#### 2.2.2 单文件 HTML 网页版：技术上完全可行

**可行的三个硬事实**：渲染层零 Node 依赖（A）+ `window.bc.*` 是唯一外部接口 + `zip.ts` 是纯 zlib 逻辑
（浏览器原生 `DecompressionStream('deflate-raw')` 即可解 `.bcproj`）。

**做法：给 `window.bc` 写一套浏览器实现（Browser Adapter）**

```
src/adapter/
  index.ts     按环境选择实现（Electron / Browser）
  electron.ts  现有 preload 原样（不动）
  browser.ts   新写：IndexedDB + OPFS + File System Access API
```

| API 类别 | 浏览器实现 |
| --- | --- |
| 工程存取 | **IndexedDB**（结构化数据）+ OPFS（大文件） |
| 导入 / 导出 `.bcproj` | `<input type="file">` 读 + `<a download>` 写（**绕开 file:// 限制**） |
| zip 解包 | `DecompressionStream('deflate-raw')` |
| 素材 | OPFS / IndexedDB Blob |
| 更新器 | 不需要（刷新即最新） |
| 系统对话框 | 自绘（项目已有 `appConfirm` / `appAlert`，天然跨平台） |

**单文件打包**：Vite 的 `vite-plugin-singlefile` 可把 JS+CSS 全内联进一个 `.html`。
当前产物 **JS 2.1 MB + CSS 515 KB** → 单文件约 **2.7 MB**，一次加载可接受。
⚠ 需处理：CSS 内对 `bc-img://` 与字体外链的引用要改成 data URI 或在单文件模式下禁用。

#### 2.2.3 关于 `file://` 的限制（你的判断是对的）

`file://` 下确实：IndexedDB 被禁、跨目录 fetch 被禁、无 Service Worker。
但**三种方案可以叠加**，而且成本几乎一样：

| 方案 | 工程管理能力 | 代价 |
| --- | --- | --- |
| **A. 单文件 HTML + `file://`（你说的"纯体验版"）** | 只做当前会话；导出靠 `<a download>` 下载 `.bcproj` | 最简单；符合"网页端不做完整功能"的定位 |
| **B. 静态托管（GitHub Pages 等）+ IndexedDB** | **真正的工程管理**（多工程 / 自动保存 / 快照） | 需要一个网址（免费）；**file:// 的限制全部消失** |
| C. File System Access API | 用户授权目录，读写真实文件 | **仅 Chromium**，但体验最接近桌面版 |

**建议 A + B 同做**：同一份单文件 HTML，双击 = 体验版（A），放 Pages = 完整网页版（B）。
预计只需新增 `adapter/browser.ts`（约 600~900 行），**渲染层一行都不用改**
—— 因为架构已经准备好了（事实 A）。

**副产品**：
- 一个链接就能让人试用，不必下载 110 MB 的包；
- 可做"URL 里带场景 JSON 的只读预览"，方便分享单个网页；
- **探针可以跑在真实浏览器里**：现在 52 个探针在 Electron 里要 11 分钟，浏览器里预计 2 分钟量级。

### 2.3 插件接口要不要彻底放开？

#### 现状（实测）

| 项 | 现状 |
| --- | --- |
| 插件宿主 `lib/pluginHost.ts` | **168 行** |
| 插件入口形态 | `(function (Bc) { ... })(Bc)` 源码字符串 |
| 执行方式 | **`new Function('Bc', source)`，在渲染进程同一 JS 上下文里求值**（CSP 已开 `unsafe-eval`） |
| 当前能力 | 注册元素、注册属性、导出前/后钩子（4 个导出函数） |
| 沙箱 | **无**（插件可触达 `window.__sceneStore`、可改 DOM、可用 `window.bc` 的全部 74 个能力） |

#### 放开的分级

| 级别 | 能力 | 实现难度 | 风险 |
| --- | --- | --- | --- |
| **L1（现状）** | 加元素 / 加属性 / 改导出 HTML | 已完成 | 低 |
| **L2（建议先做）** | + 自定义属性编辑器、+ 画布装饰层、+ 右键菜单项、+ 命令面板命令 | 中 | 中 |
| **L3** | + 任意读写场景树、+ 拦截保存/加载、+ 网络请求、+ 文件系统 | 中 | **高** |
| **L4（彻底放开）** | 直接暴露全部 `window.bc` 与 Node API | 低 | **极高** |

#### 好处

1. **一个人做不完一个编辑器**。你现在的节奏是"改一行要跑 52 个探针"，
   插件生态是唯一能把长尾需求（行业表单规范、公司设计系统、某 CSS 框架预设）转移出去的机制
   —— 这正是 VS Code 赢的方式。
2. **对你是减负**：插件作者会自己写文档、自己答疑。
3. **把你"不打算做"的功能变成别人的功能**：多页模板、导出 React 组件、接 CMS 等。
4. **L2 的投入产出比最高**：允许"自定义属性编辑器 + 画布装饰层"就能覆盖 80% 真实需求，
   且完全不需要给插件场景树的写权限。

#### 坏处（对当前阶段尤其致命）

1. **安全模型现在是零**。`new Function` + 无沙箱 + 可触达 74 个宿主能力
   = 一个恶意插件能删工程、读磁盘、发网络请求。
   一旦开始宣传插件生态，"装了个插件工程没了"会直接摧毁信任。
2. **API 公开即冻结**。v0.4.5 一轮内就重写了中键搜索、定位系统、更新器
   —— 内部结构还在快速变动期，此时公开 API 等于把自己锁死。
3. **测试负担成倍涨**。52 个探针已占满 11 分钟；再加"插件 × 功能"兼容矩阵会变成小时级。
4. **支持成本转移给你**：用户会把"装了插件坏了"记成"BlockCanvas 坏了"。
5. **`unsafe-eval` 会拖累网页版**：上 CDN 时开放 `unsafe-eval` 会显著降低安全评级。

#### 建议：分三步，先定形状、后放能力

**第一步（零成本，现在就能做）：能力白名单 + 版本化**

```jsonc
// 插件 manifest
{ "apiVersion": "1", "permissions": ["element", "property"] }
```

宿主启动插件时**只把对应能力对象传进 `Bc`**；未声明的能力在 `Bc` 上根本不存在。
不需要沙箱技术，纯"少给参数"，就能挡住大部分误用与越权。

**第二步（等真有插件作者了再做）：L2 扩展点 + 真沙箱**

- 提供 L2 的 UI 扩展点（属性编辑器 / 画布装饰层 / 命令）；
- 插件跑在 **iframe + postMessage**（或 Worker + 结构化克隆）里，**不再用 `new Function` 同上下文**
  —— 这是唯一能真正隔离的办法；
- 需要 UI 的插件走**声明式**（插件返回 JSON 描述，宿主渲染），而不是插件直接操作 DOM。

**第三步（决定做"插件市场"时）：L3 + 权限弹窗 + 签名**
像浏览器/手机那样，安装时列出"要读工程文件 / 要联网"，用户逐项确认。

**结论：现在不要彻底放开。但要把接口形状先定下来**（`apiVersion` + `permissions`），
将来放开是"加能力"而不是"推倒重来"。

## 3. 天然优势：把 Windows 变成安卓验收台

你提到"电脑完全支持屏幕竖屏" —— 这一点比看起来重要得多，但要**先解决一个阻塞**。

### 3.1 阻塞：外壳被锁在 960px

`minWidth: 960` + 外壳只有 3 条窄屏媒体查询（事实 B、C）
→ 就算把显示器转成竖屏、窗口放到最大，编辑器外壳的宽度仍然是 960px 以上，
**看不到任何手机布局**（能看到的是"被设计的那张网页"在 480/768 断点下的样子）。

### 3.2 所以第一步要做的是"解锁"，而不是"适配"

| 步骤 | 内容 |
| --- | --- |
| 1 | 解除/降低 `minWidth`（开发态可试 320，正式版可保留 720 并给一个"手机外壳预览"模式） |
| 2 | 给 `App.tsx` 加一个**外壳断点**（例如 `data-shell="wide\|narrow"`，阈值建议 720px），与画布断点解耦 |
| 3 | 窄屏外壳：左右面板改为**抽屉/底栏**，工具栏改为可横向滚动或收起，右侧面板全屏覆盖 |
| 4 | 加一个"竖屏验收"探针：窗口设为 **412×915**（Pixel 尺寸）与 **390×844**（iPhone 尺寸）跑一遍 UI 溢出审计 |

### 3.3 竖屏显示器能验证什么（这是你说的天然优势）

| 能验证 | 怎么验 |
| --- | --- |
| 手机宽高比下的**整体观感** | 窗口拉到 412×915，人眼直接看（竖屏显示器上就是全屏大小） |
| 面板抽屉、底栏、工具栏收起的**交互手感** | 键盘鼠标就能试；有触摸屏的话还能试触摸 |
| 480/768 断点下**被设计网页**的真实效果 | 现有设备组（电脑/平板/手机）已经在做，竖屏下更直观 |
| 长页面的**滚动性能** | 1080×1920 的可视区比横屏高得多，滚动掉帧更容易暴露 |
| 触摸目标尺寸是否够大（≥44px） | 竖屏下按手指比例看，比横屏更容易发现问题 |

**不能替代的**：真机触摸事件（`touchstart`/`touchend` 与鼠标事件的差异）、
Android WebView 的渲染差异、软键盘弹起时的视口变化。这三项仍需真机或模拟器。

**建议**：竖屏 Windows 作为**日常快速验收**（每次改完外壳都看一眼），
真机只做**里程碑验收**（每个阶段末尾跑一次）。

## 4. 下一轮待办（可直接执行）

### 4.1 结构重构（先做，因为后面的大功能都要动这些文件）

## 5. 明确不做（避免范围失控）

- **不做插件真沙箱（iframe/Worker）**：等真有第三方插件作者时再做（R6-22 只定形状）。
- **不做安卓打包**：先做 R6-7~R6-13（外壳窄屏化 + 网页版），
  这两件做完之后套 Capacitor 才是"接线"，现在做就是"移植 + 重新设计交互"一起上。
- **不做多页工程的完整实现**：只保留识别与数据结构预留（R6-20 视时间而定）。
- **不引入大型状态库/UI 框架替代品**：当前 zustand + 自绘组件没有出现瓶颈，
  换框架的收益远小于重构风险。
